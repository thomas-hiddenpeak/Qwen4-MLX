【文档一：M5 Max 整模型性能路线，开发顺序摘录】

### 1. 建立无 MTP 的带宽与完整请求基线

先使用当前固定引擎和原权重，不切换后端。选取真实中文、代码、项目文档和多轮请求，分别记录短输入与长输入、首 token、稳定生成段、总耗时、分配/物理内存、SSD 活动。保留请求、token 数、输出和实际采样设置。

第一轮在当前 4096 上下文内检查。长文档输入加生成必须越过 QSA 的 2048 预算对应的实际分派边界（当前源码 KV 长度超过 2051），并满足输入加输出小于上下文上限；不能用未触发稀疏路径的结果代表长上下文。扩大上下文是之后独立的内存与正确性实验。

用 Metal System Trace 与阶段计时区分权重读取、矩阵计算、CPU 提交等待、SSD 缺页和状态处理。GPU busy 百分比不能代替有效带宽或矩阵单元利用率。性能计时和带追踪的诊断运行分开进行。

固定 MTP、PLD、外部 drafter 和前缀缓存关闭，单请求运行。prefill 与稳定 decode 分开；短上下文与实际 QSA 激活后的上下文分开。初始内核带宽实验保持原 Q4/group64 权重，不把 Core ML LUT8 重编码差异混入 GPU 内核对照。

先建立每 token 的逻辑数据账本：实际选中专家的 packed Q4、scale/bias、共享专家、参与执行的主干和 head、上下文状态读写；排除不执行的专家和 MTP 参数。再单独用硬件计数器记录同一时间窗口、明确归属的 DRAM 读写。没有可用计数器时将物理带宽标为未知，仅报告估计的逻辑有效载荷速率，禁止将模型文件大小×token/s称为实测内存带宽。

物理带宽应与本机相同访问模式的持续带宽上限比较。顺序读取校准、带写入的 memcpy、随机专家访问和 SSD 读取各有不同口径；全芯片宣传峰值不能直接充当某个内核的可达带宽。优化目标同时包括减少无效流量和降低单 token 耗时，缓存复用或融合减少 DRAM 流量也可能是进步。

### 2. 优先改善已有 GPU 路径

prefill 与 decode 分别优化。prefill 检查分块尺寸、路由后每专家 token 数、M5 NAX 的实际分派和无效填充；decode 优先保持 Q4 压缩，检查 MoE 融合、权重读流量、重复同步与临时张量。

固定源码已经包含单 token MoE 的 gate/up/SwiGLU 和 down/加权归约融合路径。prefill 的排序 gather_qmm 路径存在按形状切换内核的条件，因此应先观测实际 kernel 名和耗时，再决定修改分块或内核。更大分块可能增加首 token 延迟和内存，不能一律放大。

具体源码候选：本版排序 gather 路径按 `M/E >= 4` 切换，M 是 token×top_k；本模型 512 experts/top10，因此约 205 token/chunk 后进入可使用 NAX 的 RHS 路径。当前 512 token/chunk 对应每专家平均 10 个分配；本地 NAX 内核采用 BM32（不是部分旧讨论中的固定 BM64），有效 SIMD group 仍有 16 行 tile 粒度。真实路由段长度和跨 tile 边界可能导致填充计算或重复载重，需要硬件计时确认，不能用平均行数直接宣称浪费比例。

### 3. 改善 SSD 与状态缓存

先测 n-gram 等待在完整请求中的占比。prefill 的输入 token 已知，可提前计算索引、合并重复请求并在有界缓存内复用表行。decode 只预取已经知道的当前 token 及历史对应行，尽可能与 PLE 之前的主干计算重叠；未知未来 token 的读取只能基于明确的投机候选，不能假定未来索引已知。

已有实现不能重复计作新优化：本版已使用只读 mmap、48 个常驻 pread worker，以及 layer0 前发起、PLE(layer1) 消费的异步 gather。已有单任务有界缓冲和同步回退；尚未发现独立的跨 token decoded-row LRU。应先测现有 PLE residual wait，再决定是否调整 worker 数、去重或增加小行缓存，而非重新加入已有并行读取。

不要把 51.2 GB 表全部锁入内存，也不要无条件启动大范围预取。缓存大小、预取深度、CPU worker 数按实际缺页、命中率和整模型耗时选择。

前缀缓存用于多轮/重复前缀体验。源码已支持 qwen4 的 RAM prefix cache 和包含 QSA、PLE 历史的 SSM checkpoint，也有 capture/restore 单测；当前 `--prefix-cache-entries 0` 将缓存及 checkpoint 关闭。基础 decode 带宽评测完成后，另开小容量缓存实验，检查 cache miss/hit 的输出一致性、内存和真实首 token 时间；源码支持不替代本机多轮状态等价测试。

未来组合时有额外边界：native MTP 头自己的 QSA 历史尚未通过前缀缓存的 speculative snapshots 保存/恢复，恢复前缀后会重置头并从剩余 prompt 建立历史。因此缓存与 MTP 的收益不可相乘。当前阶段不测试该组合。

【文档二：ANE Model Runner，局部 MoE 实验摘录】

## 新进展：有界并发与压缩专家

Swift 增加了 `--expert-concurrency`（默认 1，当前建议实验值 4）。不同专家可以同时提交预测；每个专家独占自己的输入缓冲并在锁内完成预测和输出复制。所有工作结束后才处理缓存淘汰，返回结果仍按原 token/slot 顺序合并。缓存容量小于并发度时自动减小每批调度数量；容量 1 保持串行。错误也等待全部工作结束后返回，避免释放正在使用的模型。

使用同一 FP16 bank，按 1/2/4/8 路正序、逆序各测一次，每组 3 次暖机、10 次计时。全部 9 个输出张量与串行逐位一致，实际专家调用数也一致：

| 完整 MoE 中位耗时 | 1 路 | 2 路 | 4 路 | 8 路 |
|---|---:|---:|---:|---:|
| decode 1 token | 2.610 ms | 2.116 ms | 1.808 ms | 1.815 ms |
| prefill 中的 2 token | 4.827 ms | 3.905 ms | 3.223 ms | 6.480 ms |

4 路在这一轮分别降低约 31% / 33% 耗时；8 路不稳定，不作为推荐值。[配对并发实验](results/moe-concurrency/report.json)。`maximumScheduledConcurrency` 记录提交宽度，不代表 ANE 内部实际并行度。`predictionMilliseconds` 是各调用耗时之和，重叠时可能超过墙钟时间；`expertPredictionWallMilliseconds` 单独记录包含输入整理和结果复制的调度耗时。

压缩路径采用公开 Core ML LUT8 接口，每 4 个输出通道共用一组 256 项码表。29 个 routed experts 从源 affine Q4 解码后的 FP16 权重重新近似编码，shared 保持 FP16。它不是原 Q4 的无损封装，也没有证明 ANE 使用原生 8 位算术。

| 压缩 bank 的完整 MoE 检查 | decode 1 token | prefill 中的 2 token |
|---|---:|---:|
| 对原权重独立 FP32 参考，相对 L2 | 0.330% | 0.360% |
| 对作者 BF16 capture，相对 L2 | 0.555% | 0.612% |
| 新一轮 4 路 FP16 配对中位耗时 | 1.872 ms | 3.300 ms |
| 同轮 4 路 LUT8 配对中位耗时 | 1.741 ms | 3.062 ms |

精度继续通过原定 FP32 0.5% / capture 2% 的局部门槛；路由 logits、专家 ID 和权重完全一致，LUT8 的串行/并发输出也完全一致。同轮压缩版耗时降低约 7%，两轮顺序互换，每组累计 20 个暖运行样本。不同轮次的绝对耗时有波动，应优先使用同轮配对结果。

匹配的 29 个 routed 专家、shared 与两份路由权重文件合计从 **300.50 MB 降至 172.22 MB（减少 42.7%）**。这是未编译模型文件大小，不含报告、编译缓存、运行内存；尚不能证明全模型能常驻 128 GiB。原始源 Q4 和 SSD 表均保留。

新的 LUT8 bank 在 4 路调度下完成独立 Instruments 硬件追踪：10 个实际 decode 专家及 FP16 shared 各 104 次具名 ANE Prediction，共 **1,144 次**，CPU_ONLY 对照为 **0 次**。复制的 shared 包被系统添加了编译 UUID；解析器仅归一化严格 UUID 后缀并保留完整原始标签，旧 FP16 trace 的回归检查也通过。prefill 的其他专家已有计算计划和完整输出验证，尚未单独记录其硬件事件。
